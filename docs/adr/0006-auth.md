# ADR-0006 — Admin authentication

- **Status:** Accepted
- **Date:** 2026-10-26
- **Phase:** P5

## Context

The admin (P6 onwards) edits every public page, reads the contact messages and holds the media library. It has one user, the owner. It must:

- resist credential stuffing, password guessing and phishing of a single factor;
- keep working on Vercel's serverless functions, with Neon over HTTP (no interactive transactions);
- be auditable, since the site is also a security showcase: [OWASP ASVS 5.0](https://github.com/OWASP/ASVS) level 2 is the bar, assessed in [docs/security/auth-asvs.md](../security/auth-asvs.md).

## Decisions

### Built in-house, after the Lucia guide

A library such as Better Auth would bring its own data model, routes and defaults for a one-user admin. The scope is small enough to write and test every part, following the [Lucia guide](https://lucia-auth.com) for sessions. The `@oslojs/*` packages that guide relies on were deprecated by their author in 2026 (no fixes to come), so the code uses Node's `crypto` instead: HMAC for HOTP/TOTP (checked against the RFC 4226 and 6238 test vectors), SHA-256, CSPRNG and constant-time comparison. Only `@oslojs/encoding` (base32), still maintained, remains.

### Password, then a second factor, always

| Step              | What                                                                                                                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Account           | Created from the CLI (`pnpm admin:create`) with its second factor: one account (a unique index allows no second row), no registration page, no default account            |
| Password          | argon2id, 19 MiB, 2 passes, 1 lane (OWASP); 15 to 128 characters, NFC-normalized; refused if found in Have I Been Pwned (k-anonymity) or if it contains a context word    |
| Unknown email     | The same work as a real check (a dummy argon2id verification): timing does not reveal accounts                                                                            |
| Second factor     | TOTP (RFC 6238, SHA-1, 6 digits, 30 s), on from the account's creation; enrolled in the CLI only, never on the web                                                        |
| TOTP secret       | 160 random bits, sealed with AES-256-GCM (`v1.<nonce>.<ciphertext>.<tag>`), the account id as associated data; the key (`TOTP_ENCRYPTION_KEY`) lives outside the database |
| Replay            | The last accepted time step is stored; a code is accepted once, in one atomic `UPDATE … WHERE last_step < step`                                                           |
| Recovery codes    | 10 codes of 120 random bits, shown once, stored as SHA-256 (ASVS accepts a plain hash from 112 bits), each usable once                                                    |
| Re-authentication | Changing the password needs the current one and a TOTP code; new recovery codes need both; revoking sessions needs a TOTP code                                            |

### The second factor is enrolled in the CLI, never on the web

The first design enrolled the authenticator at the first web sign-in. Both reviews of P5 found the flaw: whoever holds the password before the owner signs in (a leak, a reused password) enrolls their own authenticator and owns the account. Since 2026-10-26 (the owner's decision), `pnpm admin:create` shows the QR code in the terminal, checks the authenticator's first code, then creates the account with its second factor on and prints the recovery codes; nothing is written before that code matches. `pnpm admin:reset-totp` does the same for an existing account, after ending its sessions. Both need database access, which the web never grants: the web only accepts a password followed by a code.

Against a remote database, the CLI requires the real `TOTP_ENCRYPTION_KEY` (the same as on Vercel) and refuses the public development key: a secret sealed with another key could not be opened in production, and one sealed with the public key could be opened by anyone.

The TOTP window accepts the previous and the next step (RFC 6238 §5.2, clock drift), so a code stays valid up to 90 seconds; ASVS 5.0 asks for 30. The anti-replay check and the lockout below bound the risk: this deviation is recorded in the assessment.

### Sessions in the database, by the hash of their token

- **Token.** 256 random bits in a `__Host-session` cookie (`Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`). The database stores its SHA-256 only (`admin_sessions.id`): a leaked table gives no usable token.
- **Stages.** A session is at one stage: `totp_challenge` (5 min, after the password) or `signed_in` (8 h absolute, 30 min idle). Only `signed_in` opens the admin; a partial session only reaches the second step, and moves on once, in one atomic statement. Every step change creates a new token (fixation), and signing in ends the session the browser still held.
- **Checks.** The proxy redirects a request without the cookie to the login (an optimistic check that spares a render). The real check runs in every page and every action, through the data access layer (`src/features/auth/dal.ts`): a database lookup per request (React `cache`), outside any prerender (`connection()`), failing closed. An account without a second factor (a row changed by hand) has no session at all. Activity is recorded at most once a minute.
- **Termination.** Sign-out deletes the session. The security page lists the sessions and revokes a selection, or every other one, after a TOTP code. A password change ends every other session.

### Lockout without self-inflicted denial of service

Failed passwords and codes count against three keys, all keyed hashes (HMAC with `IP_HASH_SALT`), so no address or typed email is stored:

- **account from a network** (IPv4, or the IPv6 /64): 5 failures within a day lock that pair for 1 minute, doubling to an hour. An attacker elsewhere cannot lock the owner out of their own network;
- **network**: 30 failures within an hour lock it for an hour, whatever the accounts tried;
- **second factor**: 10 wrong TOTP codes within a day, from any network, lock the account's TOTP step for an hour, doubling to a day. Spreading guesses over many networks does not multiply the tries at a 6-digit code; only a password holder gets there, and recovery codes still work meanwhile.

Each attempt reserves its place before the password or code is checked: one SQL upsert per key counts it and says, from the row's latest version, whether it may go on. Parallel attempts therefore never exceed a limit (checked by hand on PostgreSQL: 60 parallel attempts get exactly the limit's checks). A right password gives its place back, with any lock its own count set: the owner, back after a lock, is not locked out by their own success, while a lock set meanwhile by a concurrent failure stays. A full sign-in clears the account's counts. A re-authentication checks the current password before the code: a stolen session guessing the password never locks the second factor. Lock durations stop doubling once capped, however high a burst pushes a count. A lock that starts on the real account is audited and emails the owner (Resend, after the response), at most once an hour. `pnpm admin:unlock` lifts every lock. Unknown emails are counted the same way: a lock reveals nothing.

### Actions are endpoints

Server actions are public POST endpoints. Each one re-checks the configuration, the origin and the session:

- **Origin.** Next.js compares `Origin` and `Host`, but lets a request without `Origin` through; the admin refuses it, and anything the browser labels cross-site (`Sec-Fetch-Site`). The `SameSite=Strict` cookie already keeps other sites' requests anonymous.
- **Fail closed.** On Vercel, a missing `TOTP_ENCRYPTION_KEY` or `IP_HASH_SALT` (or the public development key) turns the admin off. A database failure refuses, it never lets through: a test makes every repository fail in turn and checks that no flow succeeds.

### Audit log

`audit_logs` records sign-ins, failures on the real account, locks, second-factor and recovery-code events, password changes, revocations and sign-outs, with the keyed hash of the network and the user agent. Values pass through the log redactor (no password, code, token or secret), and failed inserts are logged with their SQL state only. The security page shows the latest 50 events.

### Admin surface

`/admin` is French only, outside the locale routing, with its own root layout. The proxy routes only its known pages (a test compares the list with `src/app/admin`); anything else gets the proxy's 404 page. Responses carry `X-Robots-Tag: noindex, nofollow`, and `robots.txt` disallows `/admin` once the site is indexable.

## Alternatives considered

- **Better Auth, Auth.js.** Less code, but a larger surface and data model than one account needs, and less to show.
- **TOTP enrollment at the first web sign-in.** No terminal step, but whoever holds the password first enrolls their own authenticator; replaced by CLI enrollment on 2026-10-26.
- **Passkeys (WebAuthn).** Phishing-resistant, and could be added later; TOTP with recovery codes was chosen for P5 (decided on 2026-10-25).
- **Stateless sessions (signed or encrypted cookies).** No database lookup, but no revocation before expiry, which the security page needs.
- **Recovery codes of 50 bits hashed with argon2id.** Shorter to type, but every check would cost ten argon2id verifications; 120-bit codes keep a plain hash and a direct lookup.
- **Rate limiting in Upstash.** Shared like the contact form's, but the lock must be lifted from the CLI and read with the account: the database holds it.

## Consequences

- Two secrets to set on Vercel (`TOTP_ENCRYPTION_KEY`, and `IP_HASH_SALT` already set for the contact form), the same `TOTP_ENCRYPTION_KEY` in `.env.local` when the CLI runs against Neon, and the account to create from the CLI with a phone at hand ([deployment guide](../deploy.md)). Losing `TOTP_ENCRYPTION_KEY` makes the second factor unreadable: `pnpm admin:reset-totp` then sets up a new one.
- Losing both the phone and the recovery codes needs database access (`pnpm admin:reset-totp`): there is no email recovery, on purpose.
- A forgotten or leaked password is set again from the CLI too (`pnpm admin:set-password`), which ends every session and lifts every lock. The web cannot do it alone: whoever holds a leaked password can keep the second factor locked with wrong codes, and changing the password on the web asks for a code.
- Verification is automated:
  - unit and PGlite tests (≥ 95 % of the lines of `src/features/auth`, ≥ 90 % of its branches): RFC vectors, sealing and tampering, password policy, CLI enrollment (nothing written before the first code matches, a single account), every flow and its refusals, replay, lockout and its counters (including parallel attempts), fail-closed database errors, session lifetimes, the DAL and every action;
  - E2E, on an account enrolled as the CLI leaves it: sign-in with a TOTP code, a wrong code refused, a recovery code accepted once, every admin page refused without a full session, other sessions revoked, renewed recovery codes, sign-out, lockout, accessibility and CSP;
  - Semgrep (registry rulesets) in CI.
